### 1 · FastAPI `@app.on_event` deprecated — **FIXED**

**Severity:** P2

`app/main.py` used `@app.on_event("startup")` and `@app.on_event("shutdown")`, deprecated since FastAPI v0.95. Generated DeprecationWarning on every startup and test run.

Files: `backend/app/main.py`.

### 2 · `RuntimeWarning: coroutine never awaited` in kill-switch test — **FIXED**

**Severity:** P3 (test warning only)

`test_kill_switch_get_set` patched `kill_switch_service.reset` with a bare `AsyncMock()`. The production code calls `result.get("reset")` on the awaited result; when the mock returned a generic `MagicMock`, Python's mock machinery created an unawaited coroutine on `.get()` attribute access.

**Fix:** set `return_value={"reset": True}` on the reset mock and `return_value={}` on the engage mock.

Files: `backend/tests/test_trade_desk_routes.py`.

### 3 · `IBKRRequestCoordinator` worker tasks destroyed but pending in tests — **FIXED**

**Severity:** P3 (test noise only; no production effect)

Every test that imported `ibkr_coordinator` spawned its worker tasks via `start()`. When the per-test event loop was torn down, those tasks produced `Task was destroyed but it is pending!` messages.

**Fix:** added `IBKRRequestCoordinator.stop()` — cancels and awaits all worker tasks via `gather(..., return_exceptions=True)`. Wired into `_on_shutdown()`. The existing coordinator test fixture was updated to call `stop()` directly instead of cancelling manually.

**Added 3 tests:** `test_stop_cancels_and_awaits_all_workers`, `test_stop_is_idempotent`, and `test_lifespan_shutdown_calls_coordinator_stop`. The last test is a structural guard: if `_on_shutdown()` is ever refactored and the `ibkr_coordinator.stop()` call is dropped, the test fails loudly rather than silently leaking tasks. This was explicitly requested after the observation that the lifespan conversion (#1) and coordinator cleanup (#3) were separate changes that land in the same shutdown function — a botched conversion could silently lose the cleanup.

Files: `backend/app/broker/ibkr_coordinator.py`, `backend/app/main.py`, `backend/tests/test_ibkr_coordinator.py`.

### 7 · `POST /api/mode/set` unauthenticated — **FIXED**

**Severity:** P2

`POST /api/mode/set` (and `POST /api/mode/reset-to-balanced`) had no `require_api_key` dependency. Trading mode controls the system-wide risk aggressiveness: Conservative uses 1%/trade, Scalper uses 3× (40 trades/day cap). Any caller who could reach the FastAPI layer could flip the system from Conservative to Scalper.

**The nginx basic auth question:** `DASH_USER`/`DASH_PASS` defaults to empty in every provided `.env.example`. The Caddy snippet and `docker-entrypoint.sh` both print a loud warning when `DASH_USER` is unset. So the nginx layer is **not present by default** — `require_api_key` (checked against `SECRET_KEY`) is the correct second layer, not a belt over nginx.

`SECRET_KEY` is also optional (defaults to empty), which means on a default install with neither set, `mode/set` is open. But the same is true of `execution-mode`, `approve`, `manual-trade`, and every other auth'd route — the risk posture is consistent: both empty → open, both set → double-protected. Adding `require_api_key` to `mode/set` brings it into that consistent pattern.

**Fix:** added `Depends(require_api_key)` to both `POST /api/mode/set` and `POST /api/mode/reset-to-balanced`.

Files: `backend/app/api/routes/trading_mode.py`.

### Multi-symbol risk surface expansion — OPEN (analysis, no fix applied)

The options scanner expansion from SPY/QQQ to ~59 symbols raises a concrete question: were the position risk limits designed for 1 symbol or 59?

**What holds:**
- `max_concurrent_positions = 5` (config default) is a hard portfolio-level cap enforced in `check_execution_portfolio()` — it doesn't matter if 59 or 1 symbol qualified; only 5 positions can be open simultaneously.
- Single-underlying concentration (25% of portfolio per underlying) is a hard block at both `risk_manager.approve_trade()` and `execution_portfolio_gate`. Scanning 59 symbols doesn't create 59 concentrated positions.
- Per-trade risk sizing scales off portfolio value × `risk_per_trade_pct` (1–3% depending on mode), not off watchlist size.
- The daily trade cap (balanced: 5/day hard max) bounds how many new entries per day regardless of how many symbols qualified.

**What does not hold — sector concentration enforcement:**
`risk_manager.approve_trade()` checks sector concentration as **warn-only** (appends a flag, never blocks). The Nasdaq-100 watchlist is heavily Technology; a full 5-position portfolio with NVDA, MSFT, AAPL, AMD, and META would reach near-100% Technology exposure with no hard block from `approve_trade`. The execution gate (`execution_portfolio_gate.check_execution_portfolio`) does have a hard sector block, so on the live execution path sector concentration *is* enforced. But the `approve_trade` path (used by `UnifiedRiskEngine.check()` and potentially by preview/evaluate endpoints) still only warns. This inconsistency between the two paths should be unified — either both hard-block or both warn, with an explicit policy choice recorded.

**What does not exist — correlation enforcement:**
`compute_correlation_clusters()` in `portfolio_engine.py` (threshold 0.70) computes correlation clusters for display at `/api/portfolio/heat` and for rotation review. It is **not wired into any execution gate**. Five Nasdaq-100 tech positions with pairwise correlation 0.85 would clear every check and open. The max-5-positions cap limits the damage (5 correlated positions are not 59), but the system has no mechanism to prefer uncorrelated entries when multiple symbols qualify in the same scan cycle.

**Recommended fix (not applied here):** add correlation cluster membership as a soft flag on `PortfolioGateResult` — not a hard block (computing it requires 30+ historical bars, adding latency to the execution path), but surfaced in the execution log so the operator can see "this position added to a correlated cluster."

### `UnifiedRiskEngine` / `EmotionGuard` are dead code — **FIXED**

`app/services/unified_risk.py` contains `UnifiedRiskEngine` (wraps GuardrailEngine + RiskManager + EmotionGuard) and `EmotionGuard` (pauses trading after 4 consecutive losses or tilt score > 0.75). The module docstring says "Every order must call `UnifiedRiskEngine.check()` before touching the broker." The equity.py docstring says "All signals pass through the UnifiedRiskEngine before execution." Neither was true.

**Fix applied:**

1. **Module-level singleton** (`unified_risk.py`): `emotion_guard = EmotionGuard()` at module bottom, plus a thin `check_emotion() → (bool, str|None)` wrapper so callers don't import the field directly.

2. **Startup rehydration** (`main.py` `_on_startup`): `await emotion_guard.rehydrate_from_db()` so the consecutive-loss count survives restarts. Fail-open on DB error.

3. **Record after close** (`main.py` `_poll_fills`): after `trade_recorder.record_exit()` is confirmed, calls `emotion_guard.record_trade(was_loss=..., position_size=..., baseline_size=...)` then `await emotion_guard._persist_to_db()`. Wrapped in `try/except` (fail-open).

4. **Stage 1a gate** (`trade_desk.py` `_execute_signal`): added as the first guard after the kill-switch and before market-hours checks. Imports `check_emotion` lazily, calls it, and returns a `"blocked"` result with reason `emotion_guard: <reason>` if trading is paused. Wrapped in `try/except` (fail-open) so a DB error or import error never halts trading.

### XGBoost model — deliberately not deployed; heuristic is the correct current state

**Status:** `ml/model_registry/signal_scorer_v1.pkl` exists on the host (bind-mounted read-only) but the file is absent from the repository history (`.gitignore` excludes `*.pkl`). The model was assessed and deliberately **not deployed** because it has no skill: r² = −0.173, directional_accuracy = 50.68% on n_val=442, which is below the mean baseline. Shipping it would have replaced an honest heuristic with a model that predicts worse than naive. The deployment gap was accidentally protecting the desk.

The heuristic is the **intentional current state** — not a gap. The signal scorer's `/api/health/detail` endpoint reports `scoring_mode: "heuristic"`, `loaded: false`, `usable: false` along with the model's validation metrics verbatim.

**The connection to measured signal performance:** if the system's realized win rate is ~7% target-hit (from the `signal_outcomes` label study), that measurement is against the **heuristic scorer's** confidence gate, not an XGBoost model. A future model that meets the skill threshold changes the signal selection function, which changes the win-rate baseline. Until then, performance metrics measure the heuristic.

**Prerequisite for retraining:** label space was incomplete until the expired-at-20-bars window first fired in mid-September 2026. The earliest credible label set now exists. Revisit when there are ≥ 6 months of resolved, uncensored labels and non-zero options history.
