## Unreleased — Signal record report (signal quality audit, phase 1)

- New read-only script `backend/scripts/signal_record_report.py`: how recorded signals actually turned out, by style (equity, crypto) and by style x direction, regime, confidence band and engine version. For each group: resolved count, trading days, target-hit rate, **win rate after costs** with a Wilson 95% interval, average win and loss, and **expectancy in R** (multiples of the signal's own entry-to-stop risk) with a 95% interval that resamples whole trading days. Each group gets a verdict for the proposed publication standard: insufficient sample (under 300 resolved by default), positive, negative or unproven. `--win-rate-lb 0.75` adds an optional win-rate lower-bound gate; `--json` writes the full result.
- Duplicate rows are collapsed in memory with the same survivor rule as `scripts/dedupe_signal_outcomes.py`, so the counts are real signals even before that cleanup is applied. Nothing is deleted.
- Costs are an assumed round-trip allowance (equity 10 bps, crypto 30 bps of entry), printed with every report and overridable with `--cost-bps STYLE=BPS`. They are not measured fills.
- The report says what it cannot cover: options spread signals (logged, never resolved), day trading (the resolver walks daily bars) and per-setup results (`signal_outcomes` does not record which rule produced a signal). Those are audit phase 3.
- Logic lives in `backend/app/services/signal_record.py` (pure, tested) so phase 2 can show the same numbers in the app.
- Not included, deliberately: the unique index on `signal_outcomes`. Adding it while historical duplicates remain would fail `alembic upgrade head` and so the deploy. Order: back up (`bash deploy/hetzner/backup_db.sh`), run `python scripts/dedupe_signal_outcomes.py` (dry run), then `--apply`, then add the index in its own change.
- No migration, no new environment variables, no route, no change to any signal, threshold or order path.
